# Changelog

## 0.2.66
- synthetic.new lanes are prefixed-only. The lane feed publishes no `servedModels`, so a provider that lists only `provider/<id>` aliases was emitted as the bare canonical id; for synthetic.new that id is unknown to CLIProxy (400) or names another provider's model (`kimi-k3`, `glm-5.3`). `synthetic` and `synthetic-infinite` join `devin` and `opencode-go` in `PREFIXED_ONLY_PROVIDERS` and emit `synthetic/<id>` / `synthetic-infinite/<id>`. A prefixed-only account that also lists the bare id now emits its own `provider/<id>` alias (no live Devin or OpenCode Go account lists both forms today).
- Level floors: new optional `burnMode.floors` maps an account matcher (same identity semantics as `burnMode.accounts`; `!` entries rejected) to the remaining share it keeps, e.g. `{"synthetic:*": 0.8}`. The reading is the lane's regenerating bar when the feed carries one (`meterInfo.weeklyUsed`, now parsed as `regenUsed`), else the weekly meter. A matched account at or below its floor leaves allocation the way a feed-exhausted lane does (health `exhausted`, the feed's verdict kept as `feedHealth`, `/capacity` reason `excluded: burn floor 80% reached (79.4% left)`); a matched account with no reading leaves it too (health `unavailable`, fail closed). A burn account above its floor routes before every other burn account (`burnFirst`): it can only spend what its bar holds above the floor, and a regenerating bar nothing spends wastes its regeneration once full. Result for synthetic.new (one weekly bar, +2% every 202 min, no reset): spend tracks regeneration, the bar holds at the floor (never full, never lower than the 2 runs in flight), where before burn mode sorted the lane first and drained it to the feed's 5% reserve. Accounts the feed already marks unhealthy keep the feed's verdict. Empty or missing floors decide exactly as before.
- Served-id context ceilings: new optional `contextCaps.servedIds` maps an emitted model id (case-insensitive, provider prefix kept, `(effort)`/`[1m]` ignored) to `{ maxTokens, autoCompactTokens? }`. `contextCapsEnv` (every env-carrying path) lowers whatever window it picked to the ceiling, or sets it when it picked none; it never raises a window. synthetic.new serves GLM-5.3, DeepSeek V4.1 Flash 1017 and Kimi K3 at 524,288 tokens while agents run with `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000`, so without a ceiling a long run would hit `400 Context limit exceeded` instead of compacting. The price-tier feed cannot express this: its regexes match the provider-stripped id and would cap the same model on every lane.
- Trial roles by family: a `trials.roles` entry `role:family` (e.g. `thinker:glm`) lets that role take trial arms of that family only. Plain role entries behave as before, and thinkers still take no trial traffic by default. Trial arms still pass every quality bar (`roles.minQuality`), exclusion, adapter gate and in-flight cap.

## 0.2.65
- GPT-6.1 Sol context window 890k on every path: no price cap, only the real server ceiling. OpenAI (@thsottiaux, 2026-10-11) raised GPT-6.1 Sol's Codex/Work default context 272k -> 500k (max 1M) and stated "we are not charging long context fees for GPT-6.1 Sol when drawing usage from the subscription"; the 2x input / 1.5x output surcharge above 272k now applies only to API pay-as-you-go. Our Sol lanes are subscription (ChatGPT OAuth via CLIProxy), so a 500k or 272k cap only throws context away. Live test 2026-10-22 through our CLIProxy (gpt-6.1-sol, chat completions, subscription lane): prompt_tokens 494,351 / 797,439 / 892,978 / 917,354 accepted; ~941k rejected with HTTP 400 `context_too_large` ("Your input exceeds the context window of this model"), so the input ceiling is ~922k (1.05M window minus 128k max output). New `contextCaps.solMaxTokens` (default 890000) and `solAutoCompactTokens` (default 870000) sit 32k / 52k under that ceiling (the margins tiers.mjs applies) so a client compacts instead of failing on tokenizer-estimate drift; they apply to GPT-6.1 Sol ids in every spelling the lanes serve (`gpt-6.1-sol`, `devin/gpt-6-1-sol`, decorated forms). New `contextCaps.lunaMaxTokens` / `lunaAutoCompactTokens` (default 260000/240000) keep Luna and pre-6.1 Sol ids (`gpt-6-sol`, `gpt-5.6-sol`) under the 272k price cliff. The old `solLunaMaxTokens` / `solLunaAutoCompactTokens` keys stay accepted as aliases of the Luna caps (explicit `luna*` keys win) and never set the Sol window; they no longer appear in the resolved config.
- One env builder for every path: `contextCapsEnv` builds the caps env for `decide()` (and with it burn-mode, trial and paced picks), routed reviews (0.2.61 answered `env: {}`, so a review routed to Sol ran under the agent's base-config window), kept/pinned agents and the stale-snapshot keep. A `keep` carries no env, so a kept run whose configured model is Sol/Luna is answered as a `decide` on the same configured model string (effort omitted) carrying the caps; every other kept model still answers `keep`. `/capacity` `reviewer.routing.preview` and `.last` show the emitted env.
- Sol ceiling: the configured Sol window is a ceiling. An arm's tier cap from the price-tier feed may lower it, never raise it, so no tier can push Sol past 890000/870000. The host feed's `gpt-6-1-sol` window tier moves 500000 -> 922000 (the measured ceiling) with this release; tiers.mjs derives T - 32k / T - 52k = exactly 890000/870000 from it, so the feed and the default agree (under live 0.2.61, which applies a tier cap as is, the 922k tier alone already gives routed Sol doer runs 890000/870000). A stale 500k tier would still lower Sol to 468000/448000, and a wider tier (e.g. the 1.05M window) still lands on 890000/870000. Every other arm keeps 0.2.61 semantics: its tier cap when it has one (live Luna 240000/220000), else the Luna caps for sol/luna ids. The auto-compact watermark never exceeds the max window.
- Enforce off stays the kill switch (`keep`). Runs the host never sends to the hook (no issue, human assignee, issue model override) cannot be capped by the plugin.

## 0.2.64
- Double-quantum regression lock-in. On 2026-10-22 at 12:31Z two Meta lanes each moved one weekly quantum over under one attributed run (0.72 and 0.60, confidence 0.25) and priced at 0.0105/run against the 0.0004 group prior (C* 7.1 -> 0.72) — the same unattributed-requests inflation as the 10:06Z single-lane jump, one tick in two lanes at once. The 0.2.63 guards (≥10 attributed runs, baseline within 4x of the prior) reject this shape on both counts; this release replays it as a regression test (both lanes keep the prior with `low-attributed-runs`, slots within 25% of pre-jump) so the two-lane variant stays covered. No behavior change.

## 0.2.63
- Account-weekly guards. On 2026-10-22 one weekly quantum on 0.5 attributed runs priced a Meta lane at 29x the group prior (C* 11.6 -> 6.4): the Keeper request counters count every CLIProxy request, including runs outside the ledger, while the run count covers only ledger runs, so requestsPerRun inflated ~25x and the baseline followed it. A weekly sample now prices only on >=10 attributed runs and only when its baseline agrees with the group prior within 4x; otherwise the prior is kept. The capacity view names the rejection per lane (`calibrationRejectionReason`: `low-attributed-runs` | `baseline-out-of-bounds` | `no-run-scale` | `no-evidence` | `no-median` | `no-baseline`), the attempted runs (`attemptedAttributedRuns`) and the unattributed request share (`unattributedRequestShare` = 1 - prior/baseline) per lane and per calibration group (`requestsPerRun`, `calibrationRuns`, `calibrationRequests`). Regression test replays the incident shape (one quantum, 0.5 runs, 50x baseline): the lane keeps the prior and its slots stay within 25% of pre-jump.

## 0.2.62
- AA cost carry. On 2026-10-22 the daily refresh kept every row but published the Muse slugs with cost and prices null; null-cost arms lost every ladder rung, all Meta lanes emptied and the fleet target stalled. The refresh now carries the last known cost and prices forward per slug when a refresh drops them (fresh values always win; carried rows are marked `costCarriedFrom` with the source snapshot's time and the carry logs at error level), and a scored arm with no cost or prices anywhere takes the family median, else the fleet median, flagged estimated — a served arm never leaves the ladder only because its cost is null. The `/capacity` arms report both marks (`costEstimated`, `costCarriedFrom`); views without them are byte-identical to before. Regression test: a refresh that nulls one family's costs leaves that family's ladders non-empty and the target within 10% of the previous tick.

## 0.2.61
- Per-account burn deadlines. New optional config `burnMode.deadlines` maps an account matcher (same identity semantics as `burnMode.accounts`: id, lane/accountKey, feed label/email, `provider:*`, case-insensitive) to a strict ISO-8601 timestamp with an explicit `Z` or numeric offset (a missing zone would parse as worker-local time). A burn account matching a future deadline paces to `min(regular reset, burn horizon, now + horizonMinutes, deadline)` — after the weekly reset a fresh week that must burn in 24 h paces to the deadline instead of the week — so its required rate, plan position and fleet C* need all follow the deadline. Past deadlines are ignored (a cancelled account disappears from the feed anyway). The capacity view reports each burn account's winning bound as `paceTargetAt`/`paceTargetSource` (`reset` | `horizon` | `deadline`); `paceResetAtMs` keeps its meaning (the effective pace end) and still feeds C*. Validation rejects a non-object `deadlines`, loose/unparseable timestamps and matcher keys that collide after trim + lower-casing; normalization lower-cases keys and keeps the earliest parseable stamp per matcher. Empty or missing deadlines decide bit-for-bit as before (regression test).

Routing ranked accounts by burn and plan position without asking the pace guard, and a kept reviewer with no qualifying arm fell back to `keep` (its pinned model, never paced). ## 0.2.59
- Pace guard follows the measured burn: a lane's paced slots were priced only by its estimated burn per run (`targetShare = required / E`), so when the runs on it cost more than the estimate (max-effort reviews on lanes calibrated by cheaper doer runs) the cap stayed high while the lane burned several times faster than its plan. Live 2026-10-21: the two paced Meta lanes measured 2.1%/h against 0.55%/h required at cap 4. Now an ahead lane with measured > required has its slots scaled by required/measured (floor 0.1; `laneVerdicts[].rateCorrection` on /capacity). Lanes on or behind plan, unmeasured lanes and lanes within plan are unchanged.

## 0.2.58
- Runnable kept/review demand: kept agents (`roles.keepAgentIds`) and routed review agents (`reviewerRouting.agentIds`) now count actual queued heartbeat runs via the host aggregate `agents.getQueuedRunCounts` (new manifest capability `agents.queued_counts.read`) instead of assigned open `todo`/`in_progress` cards. A Reviewer holding hundreds of idle chat-review cards with one run in flight has demand ~1, not hundreds, so stale review backlog can no longer claim the whole fleet target and strand routed agents at their running floors. Routed (non-review) agents keep issue demand. When the queued-run read is denied or unavailable, kept/review agents degrade to `queued 0` with `demandSource: 'heartbeat-runs-unavailable'` -- never falling back to assigned cards -- and grant no new slots. Every `/caps` entry reports `demandSource` (`issues` | `heartbeat-runs` | `heartbeat-runs-unavailable`) so consumers can see why an agent got its allocation. Requires the host capability; until the host ships it, kept/review demand reads running-only (still correct: no stale backlog claims capacity).

## 0.2.57

Degraded for any other reason (recent failures, cooldowns), exhausted, unavailable and non-burn accounts are unchanged. The lane parser keeps the optional feed `healthReason`.

## 0.2.53 — 2026-10-20

- Burn mode per provider account: new config `burnMode: { accounts: string[], horizonMinutes?: number (default 60) }`. An entry matches an account by id (`meta:meta-lane-3`), lane/accountKey (`meta-lane-3`), the feed's `label`/`email` when present (case-insensitive), or `provider:*` (every account of a provider); a leading `!` excludes and wins over positive entries (`["codex:*", "meta:*", "!rdugger@..."]`). A burn account paces to `min(regular reset, free-reset horizon, now + horizonMinutes)` so its required rate is maximal and it never reads ahead of plan; the pool pace guard leaves burn lanes out of its aggregation and never holds them (an all-burn pool is unpaced: `cap null`, `state 'burn'`); review-reserve holds never apply; routing sorts burn accounts first among the accounts that can serve (health, headroom, breakers, exclusions and exhaustion still apply). `/capacity` shows `burnMode: true` and `paceResetAtMs` on burn accounts and `paceGuard.burnAccounts`. The lane parser keeps optional feed `label`/`email`/`accountKey`. Validation rejects a non-array `accounts`, non-string or empty entries and a horizon below one minute. Absent/empty burnMode decides bit-for-bit as before (regression test compares hook decisions, shadow log, accounts, pace pools and review reserve).
- Per-lane pace guard: a pool is no longer judged on the mean plan position of its lanes. Each lane is judged on its own position; the pool cap is the sum of per-lane allowances (an ahead lane contributes its paced slots, a lane on or behind plan its full fair share `max(1, slots)`), and only lanes ahead of their own plan are held at the cap (`pacedAccountIds`, state `lanes-paced`). A spent lane (claude-lane-3 at 99%) no longer caps a lane far behind plan (claude-lane-4 at 11% with 4.6 days left) at one run. Single-lane pools are unchanged.
- Whole-percent meters: vendor meters tick in whole percents, so a flat 60-minute window read 0.00%/h at ~0.4%/h real burn. A per-account tick log (meter changes, 6h) lets a flat window extend back to the last tick, bounded by one quantum over the time since that tick (`rateEstimate: 'tick-extended'`); with no tick in 6h and runs in flight on the account the rate reads the one-quantum bound (`'tick-bound'`), never exactly 0. A positive window rate, thin data (null) and an idle flat account (0) are unchanged.
- Reviewer capacity across providers: `reviewer.providers` now defaults to `reviewReserve.providers` when the operator set it (else `['claude']`); an explicit `reviewer.providers` still wins. With `reviewReserve.providers: ['claude', 'meta']`, reviewer slots and `qualifiedAccountIds` count Meta and Claude lanes. The manifest no longer injects a `['claude']` default for `reviewer.providers`, so the fallback is reachable.
- Reviewer routing (opt-in): new `reviewerRouting: { enabled?, agentIds?, arms: [{ provider, model, effort? }] }`. For a run of a listed agent (default `reviewReserve.agentIds`, which defaults to `roles.keepAgentIds`) the hook picks an arm instead of answering `keep`: only healthy, non-excluded (weekly-exhausted), non-guarded accounts with headroom above the reserve (reactive lanes on health) that serve the arm's model qualify; role `excludeFamilies`, arm breakers (closed only) and, when enforced, credential readiness apply. Ranking: plan headroom before credit headroom, burn-mode accounts (the tick's identity-aware verdict, including label/email exclusions), the pool most behind its pace plan (mean `planAhead`), most remaining quota per hour to reset, arm order, then the least-loaded lane. The decision is recorded enforced on the chosen account (burn, pacing and the review reserve attribute it there). No qualifying arm falls back to `keep` (or normal routing for an unpinned agent). Accounts serving a routing arm count as reviewer-eligible.
- `/api/capacity` `reviewer.routing`: `{ enabled, agentIds, arms, burnModeTokens, provider, arm, accountId, reason, preview, last }` (tick preview plus the hook's last outcome); `{ enabled: false }` when unconfigured.
- Absent `reviewerRouting`: pinned reviewers keep exactly as before (regression test). Tests: `test/reviewer-routing.test.mjs`.

## 0.2.49 — 2026-10-17

- Arm-aware burn calibration: burn per run is measured per arm (model+effort) per calibration pool, not per account. Pooled meter deltas split across the arms that ran in the span by responsibility (each arm's prior burn times its run count, scaled to the observed delta); a pure-span sample measures its arm exactly. Pricing follows the current ledger run mix over the pacing window, with cost-anchor priors for never-measured arms, so switching doers from an expensive arm to a cheap arm raises slots within one tick of ledger evidence instead of waiting for quantized meter quanta.
- A dominant-arm change segments old-mix measurements immediately: the pooled EWMA restarts and members' persisted individual estimates are discarded until fresh per-account evidence re-accumulates (a first-seen mix that reprices the pool by more than 25% segments too, so an upgrade onto an already-switched fleet recovers on the first tick). Arm-less runs (no decision, no model) price as their own `unattributed` segment rather than vanishing from the denominator.
- Ledger decisions record effort; the shadow log exposes the decided `armId` (parity golden regenerated: only the newly visible arm id differs).
- Review-round hardening (3/5 → fix): arm keys trust the decided arm id (and effort) only for enforced hook decisions; every other record keys by the model that actually ran (unknown/pending models bucket as unattributed); unmeasured-arm priors rescale off the measured arms' anchors with measurement-era anchors recorded per arm (a switch onto lanes that no longer serve the old arm still reprices); the pooled estimate is priced from the carried value first and restarts only on a fresh sample, and a dominant-arm flip segments only past a 60% share with a >25% reprice so near-even mixes never flap smoothing; fresh counter-backed estimates re-base onto the mix-priced group baseline on a segmented tick.
- Regression: an expensive-to-cheap arm switch raises concurrency slots within one tick (`test/arm-calibration.test.mjs` pure helpers plus `test/arm-tick.test.mjs` driving the real tick: one-tick reprice and segmentation, flat-meter persistence, noise hysteresis, executed-model attribution). Full suite: 781 green.
