# Changelog

## Unreleased

### Weekly pacing (0.2.73 — 2026-10-28)
- Add a default ten-percentage-point weekly ahead hold (`pacing.holdAheadPts`; `null` opts out): idle ahead accounts receive zero new slots instead of immediately reopening the one-job minimum. Burn mode remains exempt. Per-role empty-capacity safety suspends only hard holds, retains ordinary pacing, and is reported in `/capacity.paceGuard.roleSafety`. Shared-pool caps exclude held account allowance and preserve existing running work.
- Price the weekly linear endpoint, required rate and concurrency need at 100% minus the existing explicit account floor (`burnMode.floors`), with no extra pacing remainder; report target and spendable quota without changing raw remaining readings. No new capabilities, jobs, egress, host automation or production changes.

### Added
- Alert-only failure-cluster detector (default off): failed-run events feed per-account counters in plugin state; >= 3 allowlisted failures (`claude_auth_required`, `claude_transient_upstream`, `adapter_failed`) for one account inside a 15-minute event-time window creates or updates exactly one stable-origin managed alert issue and reports `error` through plugin health until the cluster clears. Writes happen on cluster enter/exit/count-band transitions only, never per run; `timed_out` runs are excluded and the account keeps the legacy ` on provider:account` extraction. Opt in with `failureClusterAlert: { enabled: true, assigneeAgentId }`; disabled or unassigned performs zero issue writes. Adds exactly `issues.create` + `issues.update` with create/update field allowlists and per-write ownership checks; no comment, checkout, wakeup, interaction, document or relation writes, no routing or enforce-flag change, no new job, egress, secret or env key.
- Read-only `modelInventory` on `/capacity`: raw, canonical and emitted spellings of every reported model id side by side, per-account served present/absent/unknown (an absent served list reads unknown, fail-open as routing does), linked unscored/unservable/readiness evidence, and explicit unknown markers for protocol/tool/reasoning compatibility and configured-model coverage (other-agent adapter configuration is restricted). Pure reporting; routing reads nothing from it. No new capability, egress, secret or env key.
- Opt-in `freeLanes` routing for dedicated low-risk, first-attempt issue agents. Free-plan providers have shared RPM-sized additive budgets outside paid C*, a separate strict quality floor (default 0.4), optional UTC-day request reservations, and exact-arm outcome demotion (default below 80% of the last 10 measured outcomes). The outcome signal is failed runs/status progress, not adjudicated review acceptance; request budgets are estimates, not an API limiter.
- Free running counts and cap headroom stay separate from paid allocations. Existing manual exclusions, native pins, reviewer boundaries, credential-readiness mode, context caps, task-evidence trust and breakers retain authority. Synthetic and unmetered Workers AI are excluded; NIM Muse and non-`:free` OpenRouter IDs are denied. No new job, capability, external call, host script or core patch. The default-off path is unchanged.

### Fixed
- Invalidate the cached routing policy on configuration change: per-company config generations refetch a replaced source at unchanged TTL, retire the live view so the resolve hook defers instead of routing on a stale snapshot, and reject late old-generation publication. Cache hits never refresh source observation time or extend evidence/authorization expiry. No capability, egress, secret or env-key change.
- Failure-cluster alerts retain a bounded pending transition snapshot through issue-write outages and window expiry, then deliver a catch-up history on recovery. Queued maintenance respects current disable config, invalid failure timestamps fall through to valid publish times, and missing run identifiers no longer collapse distinct failures into one.
- Bound blocking-priority cap smoothing by the paid target before adding free allocations; a held paid cap cannot spend the separate free budget when both opt-ins are enabled.
- Keep free admissions outside paid per-family trial budgets, before and after each tick. Fail closed before the first free snapshot and when a stale snapshot would keep an unadmitted free default. Preserve free running floors after demotion with weak paid calibration; keep `maxConcurrentRuns` synchronized with additive allocations and prevent queued starts from exceeding the shared process ceiling.

### Blocking-priority allocation
- Retain the two newest priority snapshots per company, including pending and failed reads, so caps requests for the still-published tick cannot evict the next tick's demand snapshot. Bound retention by tick timestamp rather than request arrival order; deterministic registered-job/API overlap regressions cover active and fallback reads, shared pending requests, eviction and config invalidation.
- Validate native relation availability before using per-tick demand for the capacity target. Unavailable graphs preserve the legacy target and demand TTL as well as caps; usable graphs share fresh target/caps demand. Pin non-ready priority-root exclusion and equal-size contradictory-edge fallback with integration regressions.
- Keep active priority counts and metadata on the same fresh per-tick ready snapshot, while unavailable graphs retain ordinary demand refreshes. Reject empty, malformed or contradictory native relation snapshots, and do not amplify priority for idle routed headroom.
- Bound priority shares by useful per-agent demand and serving-pool headroom before assigning new slots. Redistribute saturated shares across eligible routed and kept agents so a tiny high-priority queue or exhausted kept pool cannot strand usable fleet capacity.
- Optional `allocation.blockingPriority` (default false) weights new-run demand by capped transitive open-card fan-out and highest ready-card priority. Active mode preserves running workloads and fits new allocations within the rounded fleet target, fleet ceiling and kept-agent serving pools; smoothing and reserved floors cannot override the split.
- Priority issue snapshots and read failures are memoized per capacity tick using only `issues.read`. Failed reads or missing native relation fields retain the legacy allocation and report `priority-unavailable`. The inspected host omits relation arrays from these SDK reads, so the feature remains inactive there until native payload support exists; no capability, core patch or host automation is added.

## 0.2.68 (deferral-exhaustion: answer the last retries instead of stranding)
- Installable on upstream Paperclip: the manifest no longer declares `agents.queued_counts.read`. The host validates capabilities against its `PLUGIN_CAPABILITIES` enum, and that capability exists only in the open upstream PR adding `agents.getQueuedRunCounts`, so declaring it rejected the whole manifest. The queued-run read stays optional: without it, kept/review demand reads running-only (`demandSource: 'heartbeat-runs-unavailable'`), as documented for 0.2.58. Re-declare it once upstream ships the capability.
- Deferral-exhaustion (Design B, default OFF). The host clamps a plugin defer to [1s, 60s] and allows RUN_MODEL_RESOLVE_MAX_ATTEMPTS = 12 retries per chain (each retry a NEW runId), so the per-runId deferredRuns marks reset every retry and can never detect exhaustion -- after the chain the card froze as blocked. New optional `exhaustion: { enabled, finalAnswerFromAttempt }` (defaults `false` / `11`): when the per-issue+agent deferral streak reaches the final attempts, the hook stops deferring and answers with the cheapest selectable free-overflow arm (nvidia-nim first) under the existing per-account reactive cap and per-family trial budget, else a bounded keep. Ignored: the pace-guard pool cap and the 5h headroom reserve (exactly the pacer bypass being priced). Never bypassed: trial role/adapter/family caps, credential readiness, the arm breaker, role exclusions, the review reserve. Metered pools ahead of plan or exhausted are never selected (a pool held only by the pace-guard in-flight cap is the explicitly priced bypass and may be selected); the bounded keep is allowed only when the agent default model serves from a healthy/degraded account -- and, for non-review runs, not from a review-reserve held account -- else the hook keeps deferring (strand rather than burn an exhausted pool or held quota). The reviewer pace-hold defer answers the same way from the final attempt; any executed run (including a stale-snapshot keep) resets the streak. Decisions record `deferral-exhausted: <prior reason> -> <arm|kept model>`; a failed scan appends per-account skip reasons to the defer reason. With `enabled: false` every terminal defers byte-for-byte as before. Memory-only, no new capability/egress/secret/env-key.

## 0.2.66
- synthetic.new lanes are prefixed-only. The lane feed publishes no `servedModels`, so a provider that lists only `provider/<id>` aliases was emitted as the bare canonical id; for synthetic.new that id is unknown to CLIProxy (400) or names another provider's model (`kimi-k3`, `glm-5.3`). `synthetic` and `synthetic-infinite` join `devin` and `opencode-go` in `PREFIXED_ONLY_PROVIDERS` and emit `synthetic/<id>` / `synthetic-infinite/<id>`. A prefixed-only account that also lists the bare id now emits its own `provider/<id>` alias (no live Devin or OpenCode Go account lists both forms today).
- Level floors: new optional `burnMode.floors` maps an account matcher (same identity semantics as `burnMode.accounts`; `!` entries rejected) to the remaining share it keeps, e.g. `{"synthetic:*": 0.8}`. The reading is the lane's regenerating bar when the feed carries one (`meterInfo.weeklyUsed`, now parsed as `regenUsed`), else the weekly meter. A matched account at or below its floor leaves allocation the way a feed-exhausted lane does (health `exhausted`, the feed's verdict kept as `feedHealth`, `/capacity` reason `excluded: burn floor 80% reached (79.4% left)`); a matched account with no reading leaves it too (health `unavailable`, fail closed). A burn account above its floor routes before every other burn account (`burnFirst`): it can only spend what its bar holds above the floor, and a regenerating bar nothing spends wastes its regeneration once full. Result for synthetic.new (one weekly bar, +2% every 202 min, no reset): spend tracks regeneration, the bar holds at the floor (never full, never lower than the 2 runs in flight), where before burn mode sorted the lane first and drained it to the feed's 5% reserve. Accounts the feed already marks unhealthy keep the feed's verdict. Empty or missing floors decide exactly as before.
- Served-id context ceilings: new optional `contextCaps.servedIds` maps an emitted model id (case-insensitive, provider prefix kept, `(effort)`/`[1m]` ignored) to `{ maxTokens, autoCompactTokens? }`. `contextCapsEnv` (every env-carrying path) lowers whatever window it picked to the ceiling, or sets it when it picked none; it never raises a window. synthetic.new serves GLM-5.3, DeepSeek V4.1 Flash 1017 and Kimi K3 at 524,288 tokens while agents run with `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000`, so without a ceiling a long run would hit `400 Context limit exceeded` instead of compacting. The price-tier feed cannot express this: its regexes match the provider-stripped id and would cap the same model on every lane.
- Trial roles by family: a `trials.roles` entry `role:family` (e.g. `thinker:glm`) lets that role take trial arms of that family only. Plain role entries behave as before, and thinkers still take no trial traffic by default. Trial arms still pass every quality bar (`roles.minQuality`), exclusion, adapter gate and in-flight cap.

New `contextCaps.solMaxTokens` (default 890000) and `solAutoCompactTokens` (default 870000) sit 32k / 52k under that ceiling (the margins tiers.mjs applies) so a client compacts instead of failing on tokenizer-estimate drift; they apply to GPT-6.1 Sol ids in every spelling the lanes serve (`gpt-6.1-sol`, `devin/gpt-6-1-sol`, decorated forms). - One env builder for every path: `contextCapsEnv` builds the caps env for `decide()` (and with it burn-mode, trial and paced picks), routed reviews (0.2.61 answered `env: {}`, so a review routed to Sol ran under the agent's base-config window), kept/pinned agents and the stale-snapshot keep. ## 0.2.61
- Per-account burn deadlines. New optional config `burnMode.deadlines` maps an account matcher (same identity semantics as `burnMode.accounts`: id, lane/accountKey, feed label/email, `provider:*`, case-insensitive) to a strict ISO-8601 timestamp with an explicit `Z` or numeric offset (a missing zone would parse as worker-local time). A burn account matching a future deadline paces to `min(regular reset, burn horizon, now + horizonMinutes, deadline)` — after the weekly reset a fresh week that must burn in 24 h paces to the deadline instead of the week — so its required rate, plan position and fleet C* need all follow the deadline. Past deadlines are ignored (a cancelled account disappears from the feed anyway). The capacity view reports each burn account's winning bound as `paceTargetAt`/`paceTargetSource` (`reset` | `horizon` | `deadline`); `paceResetAtMs` keeps its meaning (the effective pace end) and still feeds C*. Validation rejects a non-object `deadlines`, loose/unparseable timestamps and matcher keys that collide after trim + lower-casing; normalization lower-cases keys and keeps the earliest parseable stamp per matcher. Empty or missing deadlines decide bit-for-bit as before (regression test).

## 0.2.53 — 2026-10-20

- Burn mode per provider account: new config `burnMode: { accounts: string[], horizonMinutes?: number (default 60) }`. An entry matches an account by id (`meta:meta-lane-3`), lane/accountKey (`meta-lane-3`), the feed's `label`/`email` when present (case-insensitive), or `provider:*` (every account of a provider); a leading `!` excludes and wins over positive entries (`["codex:*", "meta:*", "!rdugger@..."]`). A burn account paces to `min(regular reset, free-reset horizon, now + horizonMinutes)` so its required rate is maximal and it never reads ahead of plan; the pool pace guard leaves burn lanes out of its aggregation and never holds them (an all-burn pool is unpaced: `cap null`, `state 'burn'`); review-reserve holds never apply; routing sorts burn accounts first among the accounts that can serve (health, headroom, breakers, exclusions and exhaustion still apply). `/capacity` shows `burnMode: true` and `paceResetAtMs` on burn accounts and `paceGuard.burnAccounts`. The lane parser keeps optional feed `label`/`email`/`accountKey`. Validation rejects a non-array `accounts`, non-string or empty entries and a horizon below one minute. Absent/empty burnMode decides bit-for-bit as before (regression test compares hook decisions, shadow log, accounts, pace pools and review reserve).
- Per-lane pace guard: a pool is no longer judged on the mean plan position of its lanes. Each lane is judged on its own position; the pool cap is the sum of per-lane allowances (an ahead lane contributes its paced slots, a lane on or behind plan its full fair share `max(1, slots)`), and only lanes ahead of their own plan are held at the cap (`pacedAccountIds`, state `lanes-paced`). A spent lane (claude-lane-3 at 99%) no longer caps a lane far behind plan (claude-lane-4 at 11% with 4.6 days left) at one run. Single-lane pools are unchanged.
- Whole-percent meters: vendor meters tick in whole percents, so a flat 60-minute window read 0.00%/h at ~0.4%/h real burn. A per-account tick log (meter changes, 6h) lets a flat window extend back to the last tick, bounded by one quantum over the time since that tick (`rateEstimate: 'tick-extended'`); with no tick in 6h and runs in flight on the account the rate reads the one-quantum bound (`'tick-bound'`), never exactly 0. A positive window rate, thin data (null) and an idle flat account (0) are unchanged.
- Reviewer capacity across providers: `reviewer.providers` now defaults to `reviewReserve.providers` when the operator set it (else `['claude']`); an explicit `reviewer.providers` still wins. With `reviewReserve.providers: ['claude', 'meta']`, reviewer slots and `qualifiedAccountIds` count Meta and Claude lanes. The manifest no longer injects a `['claude']` default for `reviewer.providers`, so the fallback is reachable.
- Reviewer routing (opt-in): new `reviewerRouting: { enabled?, agentIds?, arms: [{ provider, model, effort? }] }`. For a run of a listed agent (default `reviewReserve.agentIds`, which defaults to `roles.keepAgentIds`) the hook picks an arm instead of answering `keep`: only healthy, non-excluded (weekly-exhausted), non-guarded accounts with headroom above the reserve (reactive lanes on health) that serve the arm's model qualify; role `excludeFamilies`, arm breakers (closed only) and, when enforced, credential readiness apply. Ranking: plan headroom before credit headroom, burn-mode accounts (the tick's identity-aware verdict, including label/email exclusions), the pool most behind its pace plan (mean `planAhead`), most remaining quota per hour to reset, arm order, then the least-loaded lane. The decision is recorded enforced on the chosen account (burn, pacing and the review reserve attribute it there). No qualifying arm falls back to `keep` (or normal routing for an unpinned agent). Accounts serving a routing arm count as reviewer-eligible.
- `/api/capacity` `reviewer.routing`: `{ enabled, agentIds, arms, burnModeTokens, provider, arm, accountId, reason, preview, last }` (tick preview plus the hook's last outcome); `{ enabled: false }` when unconfigured.
- Absent `reviewerRouting`: pinned reviewers keep exactly as before (regression test). Tests: `test/reviewer-routing.test.mjs`.
